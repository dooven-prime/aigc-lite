# v0.7.0 → v0.8.0 upgrade acceptance

**Status:** release-candidate acceptance, not a production-history compatibility
claim. The tests must be rerun at the final release source SHA.

The published `v0.7.0` tag peels to
`834ebff7ac17f7825d8afab0c7e277f9185bd853`; its database head is
`0025_invocation_timeout`. The v0.8.0 candidate head is
`0029_shared_attempt_invalidation`.

## Runtime-written history

`tests/test_release_v0_8_runtime_upgrade.py` extracts the application code
from that exact tag into a temporary directory and imports it in a separate
Python process. The process asserts that it loaded the extracted old `app`
package and `__version__ == "0.7.0"`. Using the old application services, it
creates synthetic Claim, Artifact, proof Attempt, QualificationReceipt,
KnowledgeAdmissionReceipt, `CURRENT` binding, and active AuthorizationGrant
records. No business rows are inserted directly with SQL. The proof and
review inputs are synthetic migration fixtures, **not** mathematical
verification evidence.

After the old process exits, the test copies its SQLite database to an
isolated backup and a separate upgrade copy, stamps and checks the backup's
SHA-256, and upgrades **only the copy**. It checks that the old rows remain
unchanged; the new side table identifies the exact proof Attempt; current-use
status remains current under the new service; the old Grant can be consumed
once; and the original database and backup retain their pre-upgrade hashes.
The temporary backup and hash stamp are test artifacts, not files committed
to the repository. This uses tagged v0.7.0 application source with the test
environment's compatible dependencies; it is not a clean install of the
published v0.7.0 wheel and is not a sanitized production backup.

## Published-schema and PostgreSQL checks

`tests/test_release_v0_8_upgrade.py` separately creates the actual tagged
v0.7.0 schema and seeds **synthetic SQL rows** for exact, ambiguous, and
unreconstructable historical proof selection. It checks conservative current
use and authorization, qualified search, immutable historical Receipt/Grant
rows, pending and indeterminate Dispatch rows, a malformed-copy recovery
path, and a bounded 300-Receipt backfill. Its PostgreSQL copy test covers
database-specific migration behavior. These are useful migration and
authority regressions, but they are not old-runtime-issued PostgreSQL data.

On 2026-10-15, the two files passed together locally on Python 3.12.6 with
a dedicated PostgreSQL 17 test container: **5 passed**. This is development
evidence before the final 0.8.0 source SHA and does not transfer CI status
from an earlier commit. Run them again on the final SHA.

## Upgrade and rollback boundary

For a deployment, stop writers and external dispatch, record unresolved
dispatch identities, and take a verified backup outside the working tree.
Upgrade a copy first. If migration fails, discard that copy and restore from
the known-good pre-upgrade image; do not trust a partially migrated database
or use an in-place downgrade as a lossless rollback after new writes.
Reconcile external side effects separately. A production-history claim needs
a safely handled real historical backup in addition to this synthetic
runtime-written acceptance.
