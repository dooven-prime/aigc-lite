# v0.6.0 → v0.7.0 historical-data upgrade smoke

**Acceptance date:** 2026-10-14

**Tested source:** `77504ffbc4733a3751c1f71d18f83908f7fab88b`

**Starting release:** annotated `v0.6.0` (peeled commit `0ca02fe91dcd6e2188c91fc159eb0aab60f559f2`)
**Schema transition:** `0020_knowledge_admission` → `0025_invocation_timeout`

This is a synthetic but populated **historical-schema copy** acceptance, not a
claim that an operator's private production database was read. The test uses
the Alembic files extracted from the actual `v0.6.0` tag when that tag is
available. `git diff --name-status v0.6.0 77504ff -- app/alembic app/alembic.ini`
showed only added revisions `0021`–`0025`; the published `0001`–`0020` files
and Alembic configuration were unchanged.

## Copy, upgrade, and observed state

The regression in `tests/test_release_v0_7_upgrade.py` creates a database at
the released `0020` head and inserts one historical admitted
QualificationReceipt, its explicit KnowledgeAdmissionReceipt, a `current`
CurrentUseBinding, one active AuthorizationGrant with **one of three calls
already used**, and two unresolved external dispatches: one `dispatching`
and one `indeterminate`. The fixture also keeps their tenant, session, and
Run identity. These records are synthetic; no secrets or database files are
committed.

- SQLite: copy with SQLite's backup API, upgrade **the copy**, and verify the
  source remains at `0020` with its rows unchanged.
- PostgreSQL 17: create an isolated old database from the tagged migrations,
  populate equivalent rows, create a second database with `CREATE DATABASE …
  WITH TEMPLATE`, and upgrade **the copy**. Test-created databases are dropped
  afterward; the temporary PostgreSQL container was stopped and removed.
- Both copies reach `0025`; the five historical ledger tables retain their
  exact pre-upgrade rows. The qualification stays `ADMITTED` as a historical
  receipt, the knowledge binding stays `current` only because its separate
  admission receipt already exists, the Grant remains active with
  `calls_used=1`, and both dispatch states and the indeterminate failure code
  remain unchanged.
- Revision `0024` creates an empty `authorization_invocations` table; `0025`
  adds its timeout column. The migration does **not** invent a consumed-grant
  handoff for an older dispatch. A second active dispatch for the same adapter
  is rejected by the preserved active-slot uniqueness constraint on both
  SQLite and PostgreSQL.

**Local result:** `2 passed` for the release upgrade test against SQLite and a
temporary PostgreSQL 17 container; Ruff, byte compilation, and `git diff
--check` passed for the test source. The PostgreSQL test is opt-in via
`AIGC_LITE_TEST_POSTGRES_URL`; without that URL the same file reports one
pass and one skip. No runtime database, container log, or credential was
placed in the repository.

## Operational migration and rollback boundary

Before a real upgrade, quiesce writers and external dispatch initiation;
record the deployed `v0.6.0` commit, Alembic head, and unresolved dispatch IDs.
Take and verify a restorable database backup **outside** the application
working tree. Upgrade a copy first, compare ledger counts and identities,
then migrate the real database under a maintenance window. Do not infer that
old `dispatching` or `indeterminate` rows became safe to retry. They still
require operator reconciliation under the applicable external-enforcer
contract; absence of a new invocation handoff is not proof of nonexecution.

If rollback is required, stop the `0.7.0` process and restore the **pre-upgrade
backup** into a separately checked `v0.6.0` deployment. Do not run an in-place
Alembic downgrade on a database that has accepted `0.7.0` writes, and do not
silently merge post-upgrade authority or dispatch history into the restored
database. Preserve the failed-upgrade copy for audit and reconcile any
possibly executed external work before resuming dispatch.

## Scope and non-claims

This test checks migration preservation, readback, and active-slot behavior
for representative rows on both supported database engines. It is not a
restore drill against a real production backup, external-receipt signature
verification, cross-worker failover test, or proof that an outstanding
physical/external operation has stopped. Math 003 and SandboxBroker remain
separate research/execution acceptances and are not implied by this smoke.
