# v0.8.0 engineering candidate — acceptance plan

**Status:** candidate audit, not a release or a tagged source identity. The
package metadata still says `0.7.0`; no wheel built from this branch should be
published under that version. The proposed next core and ROS 2 bridge version
is `0.8.0`, subject to a separate final release closure.

**Starting point:** merged `main` commit
`ec5a8f769c3737adc580cc69a0359e46002a29d4` (PR #12). This is not the
eventual candidate commit; record that exact SHA and its CI run after the
candidate changes are frozen.

## Scope to accept

- Per-attempt Model Usage Receipts and explicit SSE Chat lifecycle closure.
- Read-only Host Ledger Projection, Native Goal Binding v0, and the
  Goal Progress Evidence Bridge v0.1 fail-closed diagnostic revision (see
  [its versioned contract](../GOAL_PROGRESS_EVIDENCE_BRIDGE_V0_1.md)). Goal
  identity and progress diagnosis do not authorize recovery or qualify new
  scientific evidence.
- Shared proof-Attempt invalidation across historical QualificationReceipts,
  current-use bindings, hard dependencies, qualified retrieval, Grant issue
  and consumption, and Assurance export. Historical ambiguity is represented
  conservatively; receipt history is not rewritten.
- Candidate-only Long-Horizon Recovery remains an optional casepack. Its
  replay decisions are proposals, not execution authority.

## Acceptance gates

1. **Authority consistency.** Exercise exact, historically ambiguous, and
   unreconstructable proof selection. A mathematical receipt with no reliable
   selected Attempt must not remain effectively usable just because no
   invalidation decision matches an empty index. Compare bridge v0 diagnosis
   with the authoritative qualification/current-use path on the same frozen
   snapshot. The bridge correction must carry its own v0.1 contract identity,
   rule hash, and source hashes; saved v0 responses remain historical.
2. **Historical database upgrade.** Build the schema from the actual tagged
   `v0.7.0` Alembic source at `0025_invocation_timeout`, then seed explicitly
   synthetic representative QualificationReceipts, CurrentUseBindings, Grants,
   and unresolved external Dispatch rows. This is a published-schema test,
   **not** a copy of records issued by a running `v0.7.0` application. Upgrade
   a **database copy** to `0029_shared_attempt_invalidation` or
   the eventual candidate head. Confirm source immutability, selection-index
   backfill, conservative stale propagation, preserved receipt/Grant/Dispatch
   history, and behavior after reopening the repository. Test SQLite and
   PostgreSQL where their transaction/locking semantics differ. Include a
   bounded larger historical batch and a failed-upgrade recovery check; report
   the actual sizes and timings rather than extrapolating throughput.
   A later deployment rehearsal should use a sanitized backup of genuine
   published-runtime records before claiming production-history coverage.
3. **Build and runtime closure.** On the exact candidate SHA, run Python 3.12
   tests, Ruff and byte compilation, clean wheel installations, frontend
   `npm ci`/audit/build plus packaged-asset comparison, PostgreSQL contract,
   and hardened/insecure Docker smoke. The merged-main CI result alone is
   evidence for merged-main, not for later candidate edits.

At the starting `main` SHA, [CI run 38710938902](https://github.com/dooven-prime/aigc-lite/actions/runs/38710938902)
passed all five jobs; its test job reported `667 passed, 30 skipped`, the
separate Long-Horizon Recovery casepack suite reported `36 passed`, and the
PostgreSQL job reported `33 passed`. These results do **not** certify the
uncommitted candidate changes.

**v0 diagnostic discrepancy addressed by candidate v0.1:** a synthetic historical `ADMITTED` math
Receipt with no reconstructible selected kernel Attempt can have a stored
`current` binding. The authoritative qualification refresh in this candidate
branch marks that effective use stale. Bridge v0 resolved proof selection only
when a proof-attempt invalidation decision existed and could therefore still
say `SUPPORTED_AS_OF_SNAPSHOT`. The separately identified v0.1 evaluator checks
math proof selection on every read-only assessment and returns `UNRESOLVED` on
the zero-candidate snapshot. This synthetic case does not prove a legitimately
issued old Receipt has that shape, and neither diagnostic version authorizes
execution. The stored pre-refresh `current` string alone is never a release
acceptance result. Full candidate-SHA CI and genuine historical-data upgrade
rehearsal remain separate acceptance gates.

Before production migration, stop writers and external dispatch, record
unresolved operations, and take a verified backup. A failed migration must
leave the original untouched. Rollback after new writes means restoring the
pre-upgrade backup and reconciling external side effects; it is **not** a
lossless in-place Alembic downgrade.

## Local candidate rehearsal (not final release evidence)

On 2026-10-15, this **unfrozen candidate worktree** passed a Python 3.12.6
full suite against a fresh, dedicated PostgreSQL test database: **700 passed,
9 skipped**. The separate Long-Horizon Recovery casepack suite was **36
passed**. The tagged-schema `0025 → 0029` upgrade tests were **4 passed** with
PostgreSQL enabled; their rows are synthetic, as specified above. Ruff,
`compileall`, and `git diff --check` passed. A first local full-suite attempt
against a reused test database yielded one unrelated global scheduler-count
assertion failure from a prior expired firing; the assertion was changed to
check this test's firing identity, and the fresh-database run passed.

Local clean-install smokes passed for core and ROS 2 bridge wheels, but both
still carried **`0.7.0` metadata** and are not publishable candidate artifacts.
`npm ci`, production dependency audit (zero reported vulnerabilities), frontend
build, and packaged-asset comparison passed. A uniquely tagged local Docker
image refused unsafe public startup and, with temporary test configuration,
returned healthy `/ready` (database, migration `0029`, scheduler) and the
packaged React `/ui/`. The temporary HTTP smoke container was removed. These
checks do not replace exact-commit GitHub CI or a genuine historical database
backup rehearsal.

## Package compatibility and non-claims

- `aigc-lite-mde-casepack==0.1.0` pins `aigc-lite==0.7.0` exactly. It must not
  be relabeled as compatible with `0.8.0` merely because source-tree tests
  pass. A separate casepack version and clean-installed compatibility test
  are required before including it in a `0.8.0` delivery.
- The Long-Horizon Recovery casepack remains `0.1.0.dev0` and candidate-only;
  it is neither part of the core wheel nor an authority controller.
- The ROS 2 bridge requires its own `0.8.0` build and simulator acceptance;
  this does not imply real Nav2/Gazebo or hardware acceptance.
- Math Project 003 full replay, Bio/Citation source authentication, arbitrary
  untrusted-Agent OS isolation, and cross-Run RootBudget are outside this
  engineering release. No casepack diagnostic can issue a QualificationReceipt,
  CurrentUseBinding, or AuthorizationGrant.

Do not copy the `v0.7.0` wheel hashes or CI verdicts into the new release
closure. Freeze the implementation, rerun the checks, then create a separate
`docs/releases/v0.8.0.md` only when the actual artifacts and rollback plan are
known. Do not tag from this planning document.
